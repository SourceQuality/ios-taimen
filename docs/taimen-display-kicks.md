# Why XNU's early paints did not reach the panel (analysis, 2026-10-23)

## Summary

All three XNU paint paths write the correct physical addresses and use a kick that is address-equivalent to the shim's. The decisive fact: the stage-0 path in start.s runs with the MMU off and is confirmed present in the booted binary (disassembly of out/kernels/taimen-r10/kernel.development.taimen at file offset 0x425168: `movk x0,#0x9e24,lsl 16; movk x0,#0x8400` = 0x9e248400 = 0x9d400000 + 2600*5760; 46080 x `str x1,[x0],#8` of -1; then `movk x0,#0xc90,lsl16; movk x0,#0x201c; str w1,[x0]`), and the r11 log (out/taimen-xnu-r11/xnu-log.txt:1) shows that code ran ("SWEET EARLY 0: start.s entered (MMU off)"). Yet the white band never appears. So no VA/mapping bug can be the cause; the writes land. What differs from the shim is the **START cadence**: XNU fires ~20 bare CTL0 STARTs about 1 ms apart during the first command-mode frame, which is the exact failure the port already met and fixed on Pixel 1 (patch 0099). The "noise band" is most plausibly the panel's DSC decoder output of a frame that was restarted ~100 rows in, not FB memory contents.

## (a) Addresses and kick sequences per path

1. **start.s stage 0** (osfmk/arm64/start.s:542-560, TAIMEN block after Lsweet_s0_after): MMU off, PA 0x9e248400 (64 rows white), `dsb sy`, then `str w1=1 -> 0xc90201c`, `dsb sy`. **START only** — no INTR_CLEAR, no done-wait before or after.
2. **sweet_early_band** (osfmk/arm64/sweet_early.c:39-61): `early_fb` = V=P 0x9d400000, row = early_fb + y*5760/4, 6 rows at 2000+8*stage; `early_kick` = 0xc800000 + (0xc90201c-0xc800000) = 0xc90201c; `*early_kick = 1`. **START only**, no wait, no clear. Called from every `sweet_early_mark` (sweet_early.c:161-164) for marks 0..20 until `sweet_early_disable()` at osfmk/arm/arm_init.c:544-546. After relocation (sweet_early.c:228-236) it uses the alias: FB = SWEET_EARLY_FB_VA + i*2MB for i<18, log block at +18*2MB, MDP block at +19*2MB (+0x10201c) — matching arm_vm_init.c:1861-1871 exactly.
3. **fbcon** (pexpert/arm/pe_serial.c): kickoff = ADT 0xc90201c (pe_serial.c:1047-1051); VIG0 = kick-0x1c+0x3000 = 0xc905000 (1057-1061); INTR = (kick & ~0xffff)+0x1014 = 0xc901014, CLEAR = +4 = 0xc901018 (1063-1068); DSI0 = +0x94000 = 0xc994000 (1070-1074); CTL0 LAYER0 = kick[-7] = 0xc902000, FLUSH = kick[-1] = 0xc902018 (827-832). All correct for MSM8998 (MDSS base 0xc900000); the `& ~0xffff` arithmetic is base-relative so it does not land on 8996 offsets. Kick = check done (INTR_STATUS bit 8 or 50 ms since last) -> INTR_CLEAR bit 8 -> START (pe_serial.c:788-841). Equivalent to the shim's INTR_CLEAR+START+wait, except the wait is done lazily before the *next* START.

   Two cadence bugs in the fbcon's gating: `fbcon_kick_last` starts at 0 so `now - 0 >= hz/20` makes the very first kick unconditional (pe_serial.c:783-800); and INTR_STATUS bit 8 is left *set* by the shim's final con_flush (console.c:41-48 clears before START, never after), and stage 0 / the early bands never clear it, so every done-check passes on the stale bit while an early-band frame is in flight. fbcon_init also clears all 180 rows (pe_serial.c:951-959) and each newline kicks (754-760) — all during marks 17-20, which keep firing bare STARTs.

## (b) Early mappings — no address error

- start.s:708-745: V=P 151 x 2MB blocks from 0x9d400000 (L1 index 2, L2 index 234, 278 entries left in page, one L2 page), attributes rewritten to CACHE_ATTRINDX_DISABLE; one block at 0xc800000 (L1 index 0). Both distinct from RAM's L1 index 4. The log zone at 0xb0080000 is block 150 of the same mapping and its writes demonstrably land (the kernel log exists), so block 0 (the FB) lands too.
- arm_vm_init.c:1861-1871 alias: 18 FB blocks, log block, MDP block, in the order sweet_early_relocate expects (sweet_early.c:231-235). Marks 9-20 appear in the log via that alias.
- ml_io_map_wcomb -> io_map(pa, size, VM_WIMG_WCOMB) with pa only trunc_page'd (osfmk/arm64/machine_routines.c:1583-1588, osfmk/arm/io_map.c:94-121). No transformation.
- Stage 0 is MMU-off anyway, which alone rules mapping out as the cause.

## (c) The ~100-row top band

- The photos (research/taimen/IMG_4593/4594.jpg) show the shim's *current-boot* screen (con_clear(0) at taimen.c:99 wiped the FB, then text; lines 0-1 "SHIM"/"DTB" at rows 24-120 are under the band, MMFR0 at row 120+ is crisp). The band is fine multicolour streaky noise with a sharp lower edge — the signature of a DSC command-mode panel decoding a truncated/restarted compressed stream from row 0, i.e. panel GRAM corruption, not FB content. (Stated as inference.)
- Nothing in the kernel writes ~576 KB of noise at 0x9d400000: fbcon_init clears *every* row to 0xff000000 (pe_serial.c:744-752, 956) — if its writes were displayed the screen would be black; AppleCLCD copies whole frames (SweetFramebuffer.cpp:497-518, 940-955); sweet_early writes rows 2000+ only. `grep 0x9d4` hits only start.s, arm_vm_init.c, sweet_early.c.
- ADT: dram-base 0x100000000 size 0x20000000 (mkadt.py:54,117-118), fb reg 0x9d400000/0x1000000 (mkadt.py:57,266,272). Kernel segments load at PA 0x100004000..0x1018e8000 (parsed from out/taimen-xnu-r11/payload). No allocator can hand out 0x9d4xxxxx; splash is outside RAM. Shim buffers are at 0x80080000-0x80118000 (shim log `_end`), UFS/log buffers static in that image.
- Side note (worth a look later, not this bug): the shim's rammark at PA 0x100000000 read 0xff000000ff000000 after one XNU run (shim-diag-alt-run1.txt:43) — two FBCON_BG-coloured words below the kernel's first segment; and sweet_fbcon_flip writes `(uint32_t)src` into VIG0 SRC0_ADDR (pe_serial.c:820), which truncates any IOSurface PA above 4 GB on taimen (RAM starts at 0x100000000).

## (d) MDSS 3.0 register layout

The shim's own dump is the hard evidence: INTR_STATUS at 0xc901014 reads 0x111100 = bits 8/12/16/20 = PP0 DONE / RD_PTR / WR_PTR / AUTOREFRESH_DONE (the mdp5/sde layout, PING_PONG_0_DONE = BIT(8)), and the shim's wait on bit 8 after START works (text shows). From recall of msm8998-sde.dtsi / mdp5_cfg: sde-off 0x1000 (INTR_EN 0x1010, STATUS 0x1014, CLEAR 0x1018), ctl-off 0x2000 (START at +0x1c; SDE also has CTL_PREPARE at +0xd0 but the shim proves it's not needed), sspp VIG0 0x5000, mixer 0x45000 (OUT_SIZE at +0x04, which is why the shim's LM0 +0x0 read 0), intf 0x6b800 for INTF1, pingpong 0x71000, dsi0 ctrl 0x994000. PP0 AUTOREFRESH_CONFIG 0x1 = bit 31 clear -> autorefresh off (frame count 1), consistent with the premise. The ios-flame SDE shim is for MDSS 5.x where autorefresh is on and must be disabled; not relevant here.

## (e) Proposals, ranked

1. **Stop STARTing while a frame is in flight** (highest likelihood; it is the Pixel 1 pathology verbatim, pe_serial.c:764-773 / patch 0099, re-introduced by 0185 outside the fbcon's gate). Smallest change: delete the START from `sweet_early_band` (sweet_early.c:60) and from stage 0 (start.s:556-558); the bands stay in the FB and show on the fbcon's first gated kick. Proper change: make every early kick do the shim sequence — poll INTR_STATUS 0xc901014 bit 8 with a cntpct 100 ms cap, write INTR_CLEAR 0xc901018 = 0x100, dsb, START (both registers are inside the already-mapped 0xc800000 block / alias block 19, offset 0x101014). Also in fbcon_probe set `fbcon_kick_last = mach_absolute_time()` (or treat 0 specially) so the first fbcon kick is gated too, and clear bit 8 once at probe so the stale shim bit cannot pass the check.
2. Cheap confirmation without a kernel rebuild: in the shim, after a normal con_flush, write START 20x at ~1 ms spacing and photograph; expect the same top noise band and a frozen screen.
3. Only if (1) does not fix it: the pipeline may be wedged by earlier storms (the Pixel 1 note says it can survive a warm reset) — then consider CTL0 SW_RESET / DSI command-engine reset, or ask whether the photos were taken during the XNU run or after the 31 s watchdog reset (the shim re-clears and repaints identically, so a post-reset photo cannot show XNU's bands).
4. Mapping/VA issues: ruled out by stage 0.
